# Speed Trace Analysis Report

The data generated by `tests/run_goldens.py` into `speed_trace.jsonl` is perfectly suited for analyzing the pipeline's performance. By plotting the timestamps relative to each ZID's execution, we can visualize the exact sequence and concurrency of operations.

I have created a Python script `analyze_traces.py` in your workspace root that parses this JSONL data and generates both **aggregate metrics** and a **dynamic Waterfall Gantt chart** for the latest runs in your terminal.

## Waterfall Timeline Analysis

When we project the latest traces onto a relative timeline, we can clearly see the sequential blocking nature of the current architecture.

```text

----------------------------------------------------------------------
translate_text                 | ████████████                             | 1.111s
lemmatization                  |             ███████████████████████████  | 2.507s
the_cut                        |                                        █ | 0.011s
```

### Observations for Refactoring
As seen in `ZID: 20260807232241` above:
1. `translate_text` (Network IO bound) blocks for ~1.1s.
2. `lemmatization` (CPU/Local bound) waits for translation to finish, then blocks for another ~2.5s.
3. `the_cut` fires only after both finish sequentially (3.6s total).

If the **`20260807154807-parallelize-core-and-translation`** spec is implemented via a `ThreadPoolExecutor`, these two blocks will overlap, meaning `the_cut` will fire at roughly `max(1.1s, 2.5s) = 2.5s`, directly cutting the end-user wait time by nearly 30%.

## Using the Visualizer

You can view these dynamics yourself at any time by running:
```powershell
python analyze_traces.py
```
After you implement the changes in your `openspec` plans, running this script will visually demonstrate the phases overlapping in the terminal chart, verifying that the parallelization succeeded!
